# 分块上传、队列与恢复

2026-09-08。本轮已将浏览器选择文件到 SFTP 目标的手工上传链路接入实际文件工作台；下载、持久化检查点及 AI/MCP 传输入口继续按原始范围推进，不能用本轮上传替代全部传输验收。

## 已发现的现状

旧客户端的大文件路径发送 multipart，而 uploadFileChunk 服务端从 query 读取参数并把请求当原始字节流；服务端前置 raw parser 又可能已经消耗请求。部分上传路径将 close 当作成功，直接写目标，缺少版本化提交和可靠恢复。

## 契约与状态

上传首先对浏览器选中的 File 按固定 4 MiB 块生成 SHA-256 清单，整个文件不进入单个 ArrayBuffer。prepare 绑定用户、来源清单、现有会话、请求目标和解析目标，读取覆盖基线但不写目标。start 由人工确认创建/覆盖及必要的接管后建立独占临时文件。chunk 只接受清单中的下一块，已确认块的重复提交不重复写入。finish 校验完整临时文件、重新检查目标基线、提交，再读取目标核实结果。

状态为 preview、uploading、paused、verifying、committing、completed、failed、unknown、cancelled、expired。只有完成校验和提交后的目标复核才显示完成。unknown 不自动重试提交；不把取消称为回滚。

暂停在块边界停止，释放写入占用并保留已确认偏移。恢复要重新确认浏览器来源清单、当前会话的主机身份以及临时文件已确认前缀；未确认的尾部只能在明确恢复时截回已确认偏移。重连不复用旧连接对象。源内容或目标基线改变时停止，不盲目追加。

## 责任与依赖

- types/file-upload.ts：浏览器与后端共用的清单、状态和结果契约。
- backend/files/upload-service.ts：目标预览、版本检查、检查点、提交与失败状态；只通过文件端口 I/O。
- backend/files/sftp-io.ts / ports.ts：有界散列、定点写入、截断与临时文件清理。
- backend/files/production.ts：共享文件连接、审计、提交互斥和人工写入/接管的组合入口。
- backend/hosts/file-manager/upload-routes.ts：人工身份、请求大小、参数及响应；不接受 API Key 伪装人工。
- ui/api/file-upload-api.ts：HTTP 契约，发送原始分块字节并检查确认偏移。
- ui/features/file-manager/uploads：来源 File 的内存生命周期、并发队列与中文预览/进度/暂停恢复界面。

依赖方向为文件面板 → 上传队列 → API → 上传用例 → 文件端口。上传与在线编辑在同一规范目标上共享提交互斥，人工上传期间阻止自动任务重新取得有冲突的写入机会。新增共享能力只属于文件模块，不进入无语义的 common/utils。主智能体负责实现与验证。

## 验收重点

真实 HTTP + SFTP 验证多块与空文件、字节一致性、同名目标保护、外部修改冲突、重复请求、部分写入失败、暂停后源/临时目标变动、会话归属、接管和资源释放。前端验证实际请求格式、状态转换、中文结果和取消后不假成功。全套自动/协同、MCP、文件编辑与目录查询继续回归。

检查点初期保留在当前应用会话中；跨应用重启的持久恢复和本地文件能力票据仍须后续完成。外部进程竞态不因客户端版本检查而成为原子 compare-and-swap。标准发行与完整文件工作台验收门槛保持不变。


## 当前界面与接口

文件选择、拖拽和原有文件夹上传中的文件项进入上传队列。界面显示来源校验、实际服务器与规范路径、已确认字节、速度及预计时间；每项先确认目标，已有文件默认不覆盖，也可改名后重新预览或跳过。队列默认并发 2，可在界面选择 1—4。暂停在当前分块确认后生效，恢复前重新校验整个本地来源；接管按钮只在需要时明确由人工选择。

队列保留在当前窗口的功能模块中，关闭文件标签后仍可收到完成/异常通知。退出或切换账号会中止本地发送并清除 File 引用和可见记录，后台 API 仍按原用户校验任务归属。尚未实现跨应用重启的恢复，不能把内存队列当作持久任务历史。

新接口位于 /ssh/file_manager/ssh/uploads：prepare、:id/start、:id/chunk、:id/pause、:id/resume、:id/finish、:id/cancel 以及 GET :id。chunk 使用 application/octet-stream 原始字节和 query offset，不使用 multipart；接收层限制单个原始请求为 8 MB。旧 uploadFile、uploadFileStream、uploadFileChunk 返回 UPLOAD_PREVIEW_REQUIRED，不继续直接覆盖目标或退回 shell 上传。

清单固定 4 MiB 分块，单文件最多 16384 块，当前上限 64 GiB；实际多 GiB 文件仍需后续专项验收，不能仅因数值上限存在就宣布已通过。服务端限制预览与来源清单容量，并预留并发预览名额；检查点当前按 30 分钟有效期管理。过期、来源变更或目标冲突会停止继续写入。

## 身份、取消和提交证据

hosts/accepted-host-key.ts 记录现有主机验证器已经接受的原始密钥摘要，并绑定实际 SSH Client。它不决定首次信任。上传检查点记录该密钥，跨连接恢复要求身份一致；缺失原始记录或密钥改变时，在目标 I/O 前拒绝恢复。清理也要求原服务器身份和规范父目录仍一致，只清理已确认由本次上传创建的临时路径。首次信任、跳板及指纹显示的完整 B02 行为仍在后续验证范围内。

上传与在线编辑的生产实例使用同一个 fileCommitLocks；准备目标、主机写入占用和人工接管在文件组合入口集中处理。取消遇到正在提交、已完成或未知结果时，界面保留实际状态；清理未确认时显示残留路径，不把它报成已清理。

覆盖需要支持的 POSIX rename 扩展；不支持时保留原文件并返回明确失败。新文件使用标准 SFTP rename 提交，atomic=false 表示不声明协议未提供的原子性保证。两种路径都要求完整内容校验和提交后读取验证。基本 mode/UID/GID 被保留，扩展 ACL、xattrs 与真实 Linux 权限矩阵仍待验证。外部写入者竞态仍不等于原子 compare-and-swap。
