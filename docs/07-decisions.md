## 2. 技术决策提案

### D01：统一的本地核心

建议：所有自动化入口调用同一个动作网关和会话控制器。

理由：接管、权限与记录需要在真正发送命令的地方生效。

未采用：AI 自己建立另一条 SSH 连接，人工在另一窗口“看起来像协作”。这种方式不能保证共享 cwd、程序状态或输入控制权。

### D02：优先验证现成开源底座

建议：Termix 为主候选，Tabby 为备选。Termix 的 React/TypeScript、桌面本地后端和文件工作台更贴合当前完整功能要求。此前的从空项目搭建方案降为底座不可用时的备选。

理由：优先复用已有基础产品功能，把开发集中于共享控制权、可配置策略与流程语义。详细证据见[底座评估](10-open-source-base.md)。

代价：需要严格进程边界、包体与性能验证，不能默认打开 Node 集成或远程调试。本轮调试端口只在启动检查中临时开启，检查后已关闭，见[M0 报告](11-m0-validation.md)。

若选 Tabby，沿用其 Angular 技术栈，不无理由重写为 React。Tauri + Rust 仅在完整底座均不合适时重新评估；不同时开发两套实现。

### D03：命令白名单不充当 OS 沙箱

建议：使用明确参数、作用范围、拒绝优先、审批和远端账号权限共同约束。

理由：Shell、脚本、PATH 和交互程序无法靠简单字符串黑名单穷尽分析。

未采用：黑名单未命中就显示“安全”，或把任意 shell/python 调用作为普通只读命令。

### D04：自动模式仍受限

已确认：本任务内自动执行已授权动作，包括预先授权范围内的重启服务和文件覆盖；命中 deny、未知结果、接管或预算限制就暂停。授权不跨任务自动延续。

未采用：默认无限步数、自动扩权、全服务器授权或静默切换收费模型。

### D05：流程是受控动作序列

建议：结构化参数、每步检查、定义快照、默认失败停止、不自动重试副作用。

未采用：将任意多行脚本打包后一次永久信任；将取消称为回滚。

### D06：配置元数据与凭据分离

建议：SQLite 存普通配置，OS 凭据库存秘密；安全存储失败不降级明文。

未采用：全部设置含 Key 原样存 JSON、原样云同步或导出。

### D07：首版本机 MCP

建议：stdio 适配器与本地核心经已配对 IPC 通信。首版不对外提供公网服务。

理由：外部 AI 仍能复用现有连接，同时保持身份、控制权和策略统一。

## 3. 开源方案

**最终许可随选定底座及自有代码范围确认。** Termix 上游为 Apache-2.0，Tabby 上游为 MIT；应保留上游声明、修改说明及需要的 NOTICE，不能把整套上游代码改标为自有 MIT 项目。文档阶段不生成虚构版权人的 LICENSE。

classfang/ssh-mcp-server 的公开 LICENSE 为 ISC。若后续复制或修改其代码，需要保留原版权与许可文本，并在第三方来源清单记录来源、锁定提交、修改文件和改动内容。当前没有导入其源码。

采用依赖和复制源码分别建清单，检查传递依赖、发行包资源和许可证兼容性。不能因为某个上游采用宽松许可证就推断全部依赖均已完成许可检查。

XTerminal 的公开文档作为功能参考，本稿没有其客户端源码许可依据；不将它作为可直接 fork 的代码来源。

FinalShell 同样只作功能参考。M0 已核对所选发布源码的主许可证，传递依赖与发行资源仍待完整检查；独立验证 checkout 不表示已将底座合并到 TandemSSH。

## 4. 上游事实与本项目设计分开

| 来源 | 本次核对到的事实 | 本项目的使用方式 |
| --- | --- | --- |
| XTerminal 小易文档 | 有聊天、Agent、人工确认及自定义模型配置；自定义兼容接口被列为 Pro 能力 | 参考协作信息组织；本项目自定义模型功能不设软件会员门槛 |
| XTerminal MCP 文档 | 有客户端令牌、范围和执行策略；远端命令是非交互式执行 | 参考权限呈现，不把它当作已实现共享终端接管的证明 |
| classfang/ssh-mcp-server | SSH 命令、SFTP、命令规则、exec/shell 模式；main 的包声明为 1.9.0 | 候选技术参考，复用前锁定实际提交并审查 |
| classfang 的 ISC LICENSE | 公开的 ISC 许可文本 | 复用代码时保留版权与许可来源 |

本项目的控制权版本、统一网关、流程恢复与安全要求源于本次设计。此处为初始设计记录；后续已验证与尚未验证的部分以实施记录为准。
