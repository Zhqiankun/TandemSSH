# 模型 Key 打包桌面保存、轮换与重启验证

2026-09-12，alpha.12 第二次云端发布运行期间，补充 202 的真实桌面证据。未修改生产代码。

## 实际验证

本地 alpha.12 目录版使用独立用户资料，开启测试用户 AI 偏好，通过真实 /ai/providers API 新建 OpenAI 兼容配置。模型端点为观察器创建的 127.0.0.1 HTTP 服务，只返回固定模型列表；不调用付费模型，不使用用户真实 API Key。

- 新建测试 Key 后，通过正常 models 接口读取已保存密钥，模拟端点收到正确 Authorization。
- 将 Key 换成测试短值后，返回的可见前缀为掩码，第二次模型请求使用新值。
- 正常退出应用，确认实际 db.sqlite.encrypted 为 v2/aes-256-gcm 容器，长度字段一致且不存在普通 db.sqlite；未解密文件、未读取任何加密主密钥。没有在该文件中发现完整的长测试 Key。
- 用同一隔离资料重新启动，读取相同提供方配置，第三次模型请求仍使用轮换后的 Key，证明不是仅依赖原进程内存。
- 两次客户端正常退出，模拟服务随后关闭，观察器退出码 0。

报告目录 `.cache/desktop-observation-report-9df916a6-6f81-4fa9-ac91-97046d9da26f`，最终 `result.json` 记录 3 次模型请求及重启成功。运行脚本 `.cache/run-model-key-desktop.cjs`；该脚本通过 API 操作，没有冒充鼠标填写设置表单的验证。

## 证据纠正与边界

最初观察器假设应用使用普通 db.sqlite，在路径检查时停止（9f51d17e-3b70-40e0-a52c-4d1f852e9ac8），尚未保存 Key。实际桌面 SQLite 在内存运行并把快照整体加密为 db.sqlite.encrypted。

因此，202 的 SQLite 触发器证明的是 API Key 在内部 SQL 字段中的首次明文插入，以及修复后首次就是字段密文；不能据此直接断言这次默认桌面配置曾将明文 Key 写到磁盘。外层整库加密与字段加密是两层不同保护，本次真实磁盘观察支持外层容器存在，不声称对所有旧版本或关闭外层加密的配置作出结论。

本轮不向运行中的加密数据库安装 SQL 触发器，首次 SQL 写入由 202 的真实 SQLite 专项覆盖。A16 的仅当前会话内存 Key 选项和系统加密故障桌面体验仍未完成。公开安装包仍等待 Actions，不以本地目录版代替。
